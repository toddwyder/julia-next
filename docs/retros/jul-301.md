# JUL-301 retrospective: the Shipping machine

Written from the session that built slice 2 of the shipping-trust work, 1 November 2026,
04:08–05:10 UTC. The slice is `machine/shipping`: a stock Mastra workflow whose review step
starts a fresh Execute subagent on free Beam against a pull request's own commit, and whose
determination quotes the commands the agent ran from the run's own trace file. It merged as
`86012bc` (PR #402) with main CI green, after a PASS determination on the throwaway PR #401 and
four determinations on its own PR: PASS, FAIL, PASS after the card wording was fixed.

The build worked. What cost time was six things no file recorded. Todd's review kept two of the six
fixes, sent three back, and left the sixth named for its own slice. Each item records what happened
and where it landed.

## 1. High: a draft pull request body is a cost centre, and nothing read it before CI did

The slice PR named the umbrella card and the throwaway card beside the card it ships, in prose
that read naturally. `check-branch-pr` then demanded a scorecard for every card named, CI went
red on `repository-hygiene`, and the token cannot restart a run: the only way back was to close
and reopen the pull request. Rewording the body took a minute; the cycle took ten.

Check: none in the tree. `node scripts/check-branch-pr.mjs --body <path> [--title <title>]` ran the
published rule against a draft, offline, no token, no network, and was verified on the exact body
that failed CI. Todd sent it back on 31 Oct. The lesson stands: every card key in a body is a
scorecard CI will demand, and a red run costs a close and a reopen.
Blocks now: nothing, because the check is out. The cost of a repeat is one more close and reopen.
Status: reverted by Todd, 31 Oct: one occurrence, revisit if it recurs

## 2. High: the shared Linear client read its key from a field its own message does not name

The machine's gather step called `getIssue('JUL-305')` with no options. The refusal says "pass
LINEAR_API_KEY"; the variable was set the whole time, because the key was read only from the
`apiKey` option. The run died in 28 ms. It was also invisible, because `record.json` carried no
error field, so the first read of the record showed a failure with nothing in it.

Check: `linearGraphQL` defaults `apiKey` to `process.env.LINEAR_API_KEY`
(`scripts/linear-cli.mjs:28`); a key the caller passes still wins. `getIssue` with no key argument
now reads JUL-301 from the live API through `scripts/julia-agents.mjs`. Held by four tests in
`scripts/linear-cli.test.mjs:37`, which clear the variable first so a developer's shell cannot
make them pass for the wrong reason. `machine/shipping/run.mjs` writes `error` into `record.json`.
Blocks now: a run that fails with a working key and says nothing about why.
Status: built

## 3. High: driving the harness from your own program was rediscovered by experiment, four times

Booting the harness outside the CLI cost about 45 minutes and six attempts: `session.buildToolsets`
is not a function (it is `controller.buildToolsets(session, rc)`); the subagent tool needs a
workspace; a `process.exit` right after the run leaves every table of the trace file empty while
the file looks written; one trace file holds two run ids, and the commands hang off the subagent's;
and a free model behind a custom provider is addressed as `commandcode/reflection/beam:free`, where
the bare `reflection/beam:free` fails at router config lookup.

Check: none in the tree. A section recording those five facts came back out of
`docs/harness/mastra-code.md` on 31 Oct. The working code in `machine/shipping` is the guide, and
the parent reads it before changing it.
Blocks now: nothing.
Status: reverted by Todd, 31 Oct: the working code in machine/shipping is the guide

## 4. Medium: the scorecard said a UAT yes was missing and not where it goes

`Success: not decided yet (no UAT yes recorded)` is where a reader learns the card is waiting on
Todd, and nothing said the yes is written into `docs/scorecards/uat.json`. The answer took a read
of `scripts/scorecard.mjs`. Worse, the absence looks like the scorecard's own fault.

Check: the rendered scorecard now prints the entry to write and the command to run again
(`scripts/scorecard.mjs:508`), only when the card has runs to judge and no yes. Held by two tests
in `scripts/scorecard.test.mjs:339`, which also keep it off a card that already has its yes and off
a card with no run records at all.
Blocks now: reading the script to learn the shape of the record the script wants.
Status: built

## 5. Medium: the Shipping agent failed the slice over a count in the card, and was right

Criterion 1 said the command "runs 7 tests and reports 0 failing". The retro later added an eighth
test in the same file, so the same command printed 8. The verifier read the card, ran the command,
and reported FAIL. The FAIL was correct and was written down on the card, and the card was reworded
to a condition that stays true. That is the machine working: it caught drift in the criterion, not
in the code.

Check: the Shipping agent itself. It reads the card, runs the command, and reports the drift, which
is what it did here with no written rule in place. `machine/shipping/README.md` said otherwise for
one commit, and that line came back out on 31 Oct.
Blocks now: nothing. This one was caught without a written rule.
Status: reverted by Todd, 31 Oct: the Shipping agent itself is the check

## 6. Medium: Linear work was done by throwaway scripts in `/tmp`, which are now gone

Creating the throwaway card, appending its criteria, and rewording a criterion all needed Linear

They worked, and the next slice cannot use them.

Check: add `create` and `description` to `scripts/linear-cli.mjs`, which already resolves state
names through `findStateId`. Not built in this PR: it is a capability, not a repeat of a mistake,
and it should be its own slice with its own tests. Named here so it is not lost.
Blocks now: writing card text by hand instead of from the session that produced it.
Status: not built

## Trace store

store beside 16.16 GB free, `overAlarm: false`. The largest entry is this session's own file
(6.4 GB, still open), which the launcher folds into the archive at the next launch, so the pending
