# JUL-276 retrospective: the trace-store rework and PR #381

Written from the half of session `13351dad-0d36-42f1-a43b-6e1d016cfa3e` that ran on
30 October 2026, 01:18–06:14 UTC, and ended when PR #381 merged as `6604038`. The
session before it (29 October) is the JUL-284 slice, already recorded in `jul-284.md`.

The work shipped: the trace store went from 29.5 GB to 5.7 GB, cleanup is now one command
a retro runs, and a card's cost is priced from what is published. What it cost was mostly
time spent guessing at things no file recorded, so every item below is a file that now
records one of them.

## 1. High: nothing tested how `clean` reads its own command line

`node scripts/trace-store.mjs clean <session id>` without `--card` threw
`clean needs one session id` and refused a valid call. The arithmetic that caused it
(`cardAt = -1` making `rest[cardAt + 1]` the session id) shipped inside the merged PR,
because the parser lived in `main()` and no test called it. It was found by typing the
command, twice, in a row.

The check: the flag loop moved into an exported `parseArgs(argv)`, and
`scripts/trace-store.test.mjs` calls it for a bare session id, a card, `status`, two ids,
an unknown flag and a card with no value. Shown failing with the old arithmetic put back
(`AssertionError: a session id needs no other flag`), then passing.

## 2. High: CI's `web` job fails on a Google Fonts fetch, and a push starts two runs

Two `web` runs failed in this session with
`Module not found: Can't resolve '@vercel/turbopack-next/internal/font/google/font'`
while the twin run on the same commit passed, costing about 40 minutes and one wrong
conclusion that the branch was broken. A push that has a pull request starts a `push` run
and a `pull_request` run on the same commit, and they are separate concurrency groups, so
they build at the same time. Neither can be rerun: this token has no `actions:write`, and
no `workflow` scope, so the only lever is a new commit.

The check: `docs/harness/mastra-code.md` now has a `## CI on a branch` section saying to
read the twin run and run `npm run build` locally before calling a branch broken, and
recording both token limits.

## 3. Medium: reading the store by hand took eight failed rounds

`@duckdb/node-api` is not importable from `/tmp`, `getRowsJS()` returns rows as arrays not
objects, counts come back as `BigInt` so arithmetic on them throws,
`duckdb_tables().estimated_size` is a row count and not bytes, and `octet_length` is not
implemented for `VARCHAR` here. Each one was a separate failed command, and one wrong
number (`estimated_size` read as bytes) nearly went into a report.

The check: `docs/agents/server-runbook.md` carries a "reading the store by hand" recipe —
resolve the client from the repo's `package.json`, cast before measuring, and use
`sum(length(cast(column as varchar)))` for payload bytes.

## 4. Medium: eleven edits asserted a match that was not there

Eleven failed rounds came from a scripted string replacement whose `assert old in s` guard
fired, or from the edit tool refusing with "File was modified externally" — both meaning
the text had moved, after which the session switched to `sed -i` and made it worse. Two
more lost the exit code of a pipeline: `execute_command` runs `dash`, which has no
`PIPESTATUS` and no `<(...)`, so `echo "${PIPESTATUS[0]}"` printed `Bad substitution`.

The check: `docs/harness/mastra-code.md` says a refused edit means re-read and re-apply,
and to check a pipeline through a file plus `cmp` against `git show HEAD:file`.

## 5. Small: a squash merge makes Git call the branch unmerged

`git branch -d` refused the merged branch. `git diff --stat main <branch>` was empty, which
is the proof that squashing left no work behind, so `-D` was safe.

The check: the same `## CI on a branch` section says to check that diff first.

## 6. Note: a delete in place gives back nothing, only a new file does

This retro's own cleanup deleted 52,407 span rows and 36 log rows, and the file stayed at
the same byte count:

```
before  -rw-rw-r-- 1 ubuntu ubuntu 5955137536 Oct 30 04:20 observability.duckdb
after   -rw-rw-r-- 1 ubuntu ubuntu 5955137536 Oct 30 06:19 observability.duckdb
```

Not "less than the deleted rows": nothing. DuckDB keeps the freed blocks inside the file
for reuse, and a checkpoint truncates only blocks at the end, which these were not, so the
15 GB alarm could never be answered by emptying a store in place. Measured on a scratch
copy the same day: 200k rows, delete every one, checkpoint, still 48.0 MB with 190 of 192
blocks free. A dense copy does return the space: copying the emptied 5.7 GB store gave
4.3 MB with the row counts unchanged.

So the code now gives each session its own file and deletes that file at the next launch
after copying its cost rows into an archive. Measured on a copy of the 5,955,137,536 B
store: 44,408 cost rows kept, 3,420,160 B left behind, 1.4 s.
