# JUL-321 retrospective: trace cleanup that clears every finished session

JUL-321 shipped as `9ae91ee` (PR #426) on 2 November 2026, after 1h 47m and one Shipping
round, which returned PASS. The slice made the fold read-only so a 14.2 GiB trace stopped
growing to 18.1 GiB, kept one failed trace from blocking the rest, recorded what it left
behind, and named that trace in `status` and on the scorecard of any card it carries. The
same pull request also added the machine-builder check from JUL-319.

## 1. High: a fold attached old traces for writing, and detaching one checkpointed it larger

`fold` only reads an old trace before deleting it, but both attachments were made for
writing. Detaching a write-attached trace ran a checkpoint that rewrote a 14.2 GiB trace to
18.1 GiB, filled the disk, and failed with "No space left on device". The disk was not
returned until the file was deleted, and nothing in the fold needed write access.

Evidence: `docs/agents/jul-321/decisions.tsv` row 1; `docs/agents/server-runbook.md` (14.2 GiB
to 18.1 GiB); the commit message for JUL-321.

Check: `tryAttach` now attaches with `READ_ONLY` for both attachments
(`scripts/trace-store.mjs:152-163`, called with `true` at lines 170 and 178), so a finished
trace cannot be rewritten and keeps its size until removal. Held by
`scripts/trace-store.test.mjs` ("a fold cleans a trace another process is reading") and
Shipping criterion 2, which asserts `statSync(broken).size` is unchanged.

Status: built.

## 2. High: one failed trace blocked every later trace for two days, and the quiet fold hid it

`foldTraces` stopped at the first error, so from 31 October to 2 November 2026 the oldest
failure kept every later trace in the folder from being cleaned. The launcher ran the fold
under `|| true`, so nobody saw the failure either.

Evidence: `docs/agents/jul-321/decisions.tsv` row 2; `docs/agents/server-runbook.md` (one
trace stopped every fold behind it for two days); the commit message for JUL-321.

Check: `foldTraces` wraps each `foldOne` in its own try/catch and continues, recording the
failure in `traces/left-behind.json` with its reason (`scripts/trace-store.mjs:237-250`).
The quiet fold prints the left-behind note to stderr and exits 1. Held by
`scripts/trace-store.test.mjs` ("a trace that cannot be cleaned is named and the rest are
still cleaned").

Status: built.

## 3. High: the machine's harness built no subagent tool on the next Mastra Code build

The machine boots the installed Mastra Code program to build each stage's agent. The next
build registered no subagents unless the caller named them, so the harness built no
subagent tool and every review, retro and fix stage threw before reaching its first agent,
for reasons that had nothing to do with the code under review.

Evidence: the commit message for JUL-319; `machine/shipping/harness.mjs:77-90`
(`bootHarness` now passes the three stock definitions); `scripts/check-machine-builder.mjs`.

Check: the harness passes the three stock definitions to the boot, read from their own files
because the package root only re-exports them on some versions, and
`scripts/check-machine-builder.mjs` boots one program directory against a throwaway store,
trace and app data directory and prints PASS or a FAIL that names the builder and what it
lacks.

Status: built.

## 4. Medium: a trace left behind was named but not priced, to avoid counting it twice

A crash between the insert into the archive and the delete of the file can leave the rows
in the archive as well. Pricing a left-behind trace on top of the archive would count that
card's cost twice, so a left-behind trace is named on the card it carries but its rows are
not added to the total.

Evidence: `docs/agents/jul-321/decisions.tsv` row 3; `scripts/scorecard.mjs:309-313` and
`scripts/scorecard.mjs:396-417`.

Check: `scripts/scorecard.test.mjs` ("a trace a failed cleanup left behind is named on the
card it carries") asserts the card's tokens are `[1000]`, not `[1000, 77]`, and that the
skipped message names `left.duckdb.folding` and its reason.

Status: built.

## 5. Medium: a trace parked in `traces-hold/` is outside the store until moved back by hand

Nothing in `trace-store.mjs` looks in `traces-hold/`. A trace parked there is invisible to
`status` and to `fold` until it is moved back into the traces directory, where the card says
it becomes part of the next fold. The fold only reads the traces directory.

Evidence: `docs/agents/jul-321/decisions.tsv` row 4 ("nothing in trace-store.mjs looks in
traces-hold"); `scripts/trace-store.mjs` (`tracesDir` and `pendingFiles` only read the traces
directory).

Check: none.

Status: open (accepted as a manual parking lot; the hold folder is not part of the store).

## 6. Medium: `status` must never be the reason a cleanup fails

Asking what is left behind must stay read-only. `status` filters `left-behind.json` against
the files actually on disk and opens nothing, so a stale or half-written record cannot stop a
cleanup or be mistaken for a live file.

Evidence: `docs/agents/jul-321/decisions.tsv` rows 5 and 6; `scripts/trace-store.mjs:280-290`
and the comment above the filter.

Check: `scripts/trace-store.test.mjs` ("status reports every trace file and the alarm without
opening one"); `status` opens no database.

Status: built.

## What the machine should keep doing

Keep folding on every launch with `--quiet` so a failed cleanup is said out loud instead of
vanishing; keep every finished trace attached `READ_ONLY`; keep one failed trace from
stopping the rest; keep recording failures in `left-behind.json` and clearing them on a later
successful fold; keep `status` read-only; keep naming a left-behind trace in the scorecard of
any card it carries until it is cleared; and keep running `scripts/check-machine-builder.mjs`
after any upgrade of the installed Mastra Code program.
