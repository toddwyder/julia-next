# Mastra observability for the server dashboard — 2026-10-18

## Question

Can `/julia-control` read Mastra's own persisted records (the records behind Studio) to show an in-progress standard Mastra agent run, its model activity, tool activity, timing, and spend, without asking the agent to write a progress report?

## Installed source examined

`ops/mastra-agents/reviewer/node_modules/@mastra/core/package.json` identifies the installed Core as **1.75.0**. The installed documentation is the version-matched source for this note; the `@mastra/observability` package is not installed in this checkout, although Core's bundled documentation and type declarations describe its integration.

## Findings

1. **Mastra can persist the data Studio displays, but only when an observability storage domain and storage exporter are configured.** The installed Studio documentation says its Metrics, Traces, and Logs views all require an observability storage backend, and its quickstart configures `MastraStorageExporter` specifically to persist events to Mastra Storage ([`docs-studio-observability.md:5-44`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/docs/references/docs-studio-observability.md#L5)). The storage map defines the `observability` domain as “Traces and spans used by observability exporters and Studio” ([`reference-storage-overview.md:9-25`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/docs/references/reference-storage-overview.md#L9)). This is a required deployment/configuration fact; the package alone does not establish that the server presently stores these records.

2. **The persisted trace model has a root span for a standard Mastra agent run and timestamped children for model and tool work.** `SpanType.AGENT_RUN` is documented as the root span for agent processes; `MODEL_GENERATION`, `MODEL_STEP`, `MODEL_INFERENCE`, and `TOOL_CALL` identify model and function/tool activity ([`tracing.d.ts:22-58`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/observability/types/tracing.d.ts#L22)). A stored span has `traceId`, `spanId`, `parentSpanId`, `name`, `spanType`, `startedAt`, optional `endedAt`, input/output/error, and metadata ([`tracing.d.ts:45-86`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/storage/domains/observability/tracing.d.ts#L45)). Thus a reader can compute elapsed time and render a chronological, source-recorded activity timeline.

3. **Filesystem/sandbox/search actions are only visible when the executing adapter emits Mastra workspace spans.** Core has a `WORKSPACE_ACTION` span type for filesystem, sandbox, search, skill, mount, and computer activity ([`tracing.d.ts:82-88`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/observability/types/tracing.d.ts#L82)); its attributes record the category, provider and success flag, with operation inputs/outputs on the span ([`tracing.d.ts:788-805`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/observability/types/tracing.d.ts#L788)). A generic external Codex or CommandCode process will not become these records merely because Mastra launches it. The dashboard requirement to *always* list files, research, changes, commands and tests therefore needs an adapter-level evidence contract for each non-Mastra execution surface, backed by that surface's own records.

4. **Cost is recorded as estimated cost, not a universal authoritative provider bill.** The cost context has optional `provider`, `model`, `estimatedCost`, `costUnit`, and `costMetadata` ([`metrics.d.ts:57-68`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/observability/types/metrics.d.ts#L57)). Stored metric records carry that data with model/provider and trace/span identifiers ([`reference-observability-metrics-queries.md:192-238`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/docs/references/reference-observability-metrics-queries.md#L192)). The documentation also warns that metrics are asynchronously buffered, so quickly running agents can temporarily exceed a cost threshold before persisted data catches up ([`reference-processors-token-cost-control.md:20-25`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/docs/references/reference-processors-token-cost-control.md#L20)). For the brief's rule, the provider-reported cost should be preferred whenever an adapter exposes it; Mastra estimated cost is a visibly-labelled fallback, not proof that current provider pricing was used.

5. **The reader interface is already an incremental query surface.** `ObservabilityStorage` provides `listTraces`, `listTracesLight`, `getTrace`, `getStructure`, `getBranch`, and `getSpans` ([`base.d.ts:104-155`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/storage/domains/observability/base.d.ts#L104)). Trace listing supports filters for entity, `runId`, `sessionId`, `threadId`, timestamps, span type, trace id, and status ([`tracing.d.ts:818-925`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/storage/domains/observability/tracing.d.ts#L818)); metrics support raw listing plus a delta mode for incremental polling ([`reference-observability-metrics-queries.md:159-190`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/docs/references/reference-observability-metrics-queries.md#L159)). A dashboard reader can therefore poll persisted records rather than scrape Studio or duplicate tracing.

6. **Studio confirms the same intended read model, not a dashboard-ready business state model.** It displays traces for agents/workflows with model calls, tool executions and workflow steps, and can show duration, tokens, estimated cost and custom metadata columns ([`docs-studio-observability.md:75-95`](../../ops/mastra-agents/reviewer/node_modules/@mastra/core/dist/docs/references/docs-studio-observability.md#L75)). It does not define card stage, build/review round, provider-maker separation, context-fill percentage, compaction/handoff, “looks stuck”, or a reviewer verdict. Those must come from the delivery/run interface and the provider adapters; they cannot honestly be inferred from an arbitrary trace.

## Consequence for the brief

The stated Mastra premise is supportable for **standard Mastra agent** execution once storage and exporter configuration is shown on the OVH server. It is not enough for model-neutral dashboard completeness. The unresolved fact question is:

> For each permitted builder/reviewer adapter (Mastra standard agent, Codex, CommandCode), which provider-owned or adapter-owned record supplies: run identity, lifecycle/round, model and maker, current context/compaction/handoff, reported or price-derived spend, every requested work event, and final verdict?

Until that interface is evidenced for all three, “Everything except the labelled checklist comes from the tools' own records” remains an unproven cross-adapter contract rather than a property Mastra supplies.
