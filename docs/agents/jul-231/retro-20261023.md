## 1. High: completion checked the new listener but missed Todd's actual route

The first closeout called both cards Complete after proving two generic user services, their main commit and loopback HTTP responses. Todd then requested a broader readback. It showed `julia-control.service` still serving `/opt/julia-control`, while Tailscale Serve still proxied port 43123. The stale user file was named `julia-control-jul231.service`, outside the observer's two-name `legacyServices` list. This was my verification error: sufficient evidence to show the new listeners worked was treated as evidence that the service migration was complete.

**Candidate: extend the existing deployment proof, rather than add a policy paragraph.** Inventory Julia units in both systemd scopes and their installed files, inspect actual process paths and the Serve target, and request the control page through the tailnet URL. Check that this route reaches the expected main service. Use that inventory to identify obsolete installations and verify the specifically authorized removals; do not automatically delete every Julia unit. Local health remains useful, but cannot establish which backend the household URL reaches.

The existing `server-main.mjs` and three updater tests check advancing main, merge admission and retries. They do not exercise a competing system control service or the Serve configuration. Add those conditions to the existing deployment test/proof surface: an old system backend and a Serve target on 43123 must fail the migration verdict; the intended backend on 43126 and an HTTP 200 through the tailnet URL must pass. Keep local fixtures for the logic and a real server readback for deployment.

Evidence: [before cleanup](evidence/retro-20261023/before-cleanup.txt), [after cleanup](evidence/retro-20261023/after-cleanup.txt), [existing updater tests](evidence/retro-20261023/merged-service-tests.mjs). Cleanup removed the old system service and installation, secrets reference file and stale user unit, cleared the failed proof entry, and switched Serve to 43126. The new service also needed `JULIA_CONTROL_TAILSCALE_HOST=ovh.tail91f394.ts.net`: a request with that Host returned 403 before configuration and 200 afterward. An actual HTTPS request through Serve returned 200 before the old service was removed and again after removal. The retained raw readback records the final route. These are maker self-checks.

## 3. Medium: a green framework lint job currently checks an absent directory

CI already runs package tests, browser tests, server-owned tests, `npm run lint:framework` and the application build. This is not a repository without checks. However, `lint:framework` defaults to `graph/langgraph`; the ESLint config also targets that directory. The live command returned `graph/langgraph does not exist yet; passing.` The Standards review retained the same result as an exit-zero check. It supplies no lint coverage for the current runner/framework code.

**Candidate: repair the existing lint target and its empty-target behavior.** First decide which existing framework rules apply to the current Mastra code; blindly applying old rules banning direct writes and timers to service infrastructure would be misleading. Wire the applicable source paths into the existing job and retain a deliberate violation that makes the CLI fail. When a required target resolves to no files, report that explicitly instead of claiming those files passed lint. This is a deterministic tooling issue, so it belongs in the check rather than CODING_STANDARDS.md.

Evidence: [CI workflow](evidence/retro-20261023/merged-ci.yml), [lint implementation](evidence/retro-20261023/merged-lint-framework.mjs), [actual command output](evidence/retro-20261023/framework-lint.txt). No lint configuration was changed during this retrospective.
