Recommend CI A and maintenance A. CI A's server dispatch is not yet a complete executable design: GitHub-hosted CI cannot run server-only tests merely by producing a routing plan. Since runner administration returns 403, use an installed, independent server test poller with ordinary signed-in `gh` commit statuses. It must observe open PR heads, fetch and check out the exact head SHA in an isolated checkout, install every discovered test owner's locked dependencies, execute that head's server-owned tests through the provisioned server key wrapper, and publish a stable status context on that SHA. Mark pending before execution and success only after the complete server test command succeeds. An empty server set must also reach an explicit successful result. Polling the same SHA repeatedly must not rerun completed work; a new head needs a distinct run. Keep its state and lifecycle independent of the maintenance observer. The CI aggregate must require/read this exact server status; otherwise a green PR could omit all live tests.

Nearest package plus lockfile is the right dependency boundary, and `server` ancestry is the right declared execution boundary. Reject orphan/ambiguous ownership rather than silently falling back when a nested package lacks its own lockfile. Discovery should operate on the checked-out candidate's tracked source files and distinguish a package boundary from ordinary nested folders. Fixture proof should add a new ordinary test, nested-package test, and server test without changing lists, then execute observable assertions. Replay the actual SDK regression under the SDK owner's installation; prove the deleted orphan path is absent from both tracked source and the complete execution plan. A routing-only printout does not prove dependency resolution.

Maintenance A is the smallest installed option. Its merge recognition must inspect every newly gained first-parent commit and validate associated PR metadata using matching merge_commit_sha and watched base branch, so squash and rebase merges are covered. A normal two-parent merge is recognized directly. Baseline installation starts at current head without launches. Serialize observation and durable claim creation; write the claim durably before spawning. Repeated polls and service restarts must preserve one launch per merge identity. A crash after claim creates a blocked record, not an automatic second session. Define force-push/diverged-cursor behavior explicitly; do not replay history as new merges.

The filesystem mount and controller checks together enforce skill-only corrections. A writable Git metadata mount alone must not let the worker bypass the final path validation: publish from the checked working tree's validated diff, reject staged or committed product changes, and compare against the exact merge base revision. Permit runtime output only in disposable ignored paths. Move verification helpers into their owning skill first if corrections would otherwise require a forbidden root-source change. Preserve the maintenance skill's genuine live verification and its required source readers; a synthetic clean result is not the requested proof.

The throwaway-branch proof must exercise the installed production observer and launcher: baseline/no merge yields zero launches; a pushed real merge yields one fresh Codex thread/session ID; observing it again yields no second launch. Record the actual outcome and demonstrate both a rejected product write and an allowed skill-folder write with the real sandbox. Ordinary new commits must not create maintenance launches. Supplement with a squash-associated-PR fixture or actual metadata readback so squash support is evidenced. A branch merge containing the product candidate should use the candidate's verification skill, not a previous main revision.

Spending remains $0. Keep live-provider test execution confined to the established free machinery route; do not make an automatic status poller invoke a paid real-build/review role. Fresh signed-in Codex maintenance uses the existing authorized CLI route and no new provider billing configuration.
