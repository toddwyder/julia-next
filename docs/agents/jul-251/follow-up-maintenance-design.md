# JUL-251 maintenance architecture grounding

Observed on 23 October 2026 UTC in /home/ubuntu/julia-hybrid-pstack-trial. No repository files or deployed configuration changed by this investigation.

## Current architecture

- No maintenance cron or user service exists. `crontab -l` reports no crontab. `systemctl --user list-units --type=service --all` has only desktop/session services. System timers are OS timers.
- Existing deployed Julia control service is /etc/systemd/system/julia-control.service. It is a separate julia-control user and runs /usr/local/bin/julia-control-run, serving the control page. It is not a merge listener. Do not add maintenance to its process or credential route.
- Existing ordinary signed-in GitHub identity is toddwyder via gh. Origin is https://github.com/toddwyder/julia-next.git. The trial uses GIT_DIR=.julia/git and a linked .git. Its local origin/main ref is absent, so a listener needs its own clone and explicit remote branch fetch.
- Codex CLI is installed at /usr/local/bin/codex, version 0.163.0. Its package README was read at /opt/node-v24.14.1/lib/node_modules/@openai/codex/README.md. The README documents signed-in ChatGPT execution. `codex exec --help` documents fresh exec, --ignore-user-config, --output-schema, --json, --sandbox, --cd, --output-last-message, --ephemeral, --ignore-rules. Use fresh `exec`, never resume or fork. No provider API key or paid model route is needed.
- `systemd-run --user --wait --pipe --collect /usr/bin/true` succeeds. `bwrap --ro-bind / / --proc /proc --dev /dev -- true` succeeds. Both are installed. There is no need for a new host or GitHub self-hosted runner installation.
- Exactly one project verification skill has a feature map today. `.agents/skills/verify-julia/features/README.md` exists. Discover target skills structurally by a skill-local SKILL.md plus features/README.md and verify-* folder, rather than storing verify-julia in a list. verify-machine has no feature map and is not a project verification-skill candidate under maintain-verification-skill.
- `.agents/skills/maintain-verification-skill/SKILL.md` explicitly requires source subagents, a live pass, skill-folder-only changes, and outcomes clean/changed/blocked. It forbids product edits and scratch-note commits. verify-julia currently invokes a repository-root helper, so the session must read product source and run product/browser dependencies while writing only skill-owned source and disposable runtime output.

## Data shape

A merge observation has repository, watched branch, merge SHA, prior cursor, and discovered skill paths. A maintenance run is keyed by repository + watched branch + merge SHA. Its durable state is claimed, running, clean, changed, or blocked, with process/session identity and paths to stdout JSONL, structured result, and optional PR. One merge starts one fresh coordinator session which runs the maintenance skill separately for each discovered target. A session does not start per poll or per skill. Duplicate observation reads the existing run. A claimed run whose launch died is blocked with its evidence, not blindly relaunched.

## Sketch A. Server polling and isolated writable skill mounts. Recommended.

Install a small user systemd timer/service on this existing server. Every poll fetches only the watched branch in an independent bare/cache clone. On installation record its current head as baseline and do not retroactively maintain old merges. Each poll walks newly gained first-parent commits. True merge commits have multiple parents. Squash/rebase PR merges require GitHub's associated-pull-request metadata with merged_at, merge_commit_sha and base branch readback, rather than assuming all merges have two parents. Deduplicate by merge identity in durable state under ~/.local/state/julia-verification-maintenance. Acquire an exclusive lock for observation/claim. No new merge means no Codex process.

For each claimed merge create an isolated detached clone at the exact merge SHA, prepare locked dependencies using the appropriate owning lockfile, and launch one fresh signed-in `codex exec` in a bubblewrap mount namespace. Bind the repository read-only. Bind only each discovered verification skill directory writable. Bind disposable `.next`, `.artifacts`, browser output, node_modules, Git metadata, and scratch/run paths writable where required for the real live pass. Keep user auth/session storage available in the sandbox. Product source remains read-only as a filesystem property. The parent process also checks the entire Git diff, rejecting every changed path outside the discovered skill folders before publication. Any needed correction to a root helper is blocked, unless the helper has already been moved into its owning skill as part of this follow-up. Root product files cannot be edited even if an agent forgets the prompt.

Use an output schema for outcomes. The session executes maintain-verification-skill, but publication should have one controlling owner. A controller that alone publishes a single combined corrections PR can validate the exact diff and require supplied proof. The prompt must explain that clean has no branch or PR; changed must provide live evidence and a scoped diff; blocked emits one line to Todd and creates no PR. Sending that line should use the already-authorized Julia card/reporting route, not introduce a new chat integration. A per-run report file can be the durable Todd surface if the parent report makes its location clear.

Proof uses the production observer and launcher with branch configuration overridden to a throwaway branch. Seed its baseline, observe no merge and show zero session records. Make and push a genuine test merge on that branch, poll twice, and show exactly one durable claim, one actual fresh Codex thread.started/session ID and one outcome. Another non-merge branch update must produce zero additional maintenance starts. A synthetic callback returning a canned result is insufficient. Also execute a product write and a skill write inside the real mount configuration to prove the former fails and the latter succeeds. Restore the skill change before the real maintenance session.

Advantages. Uses installed tools and no externally exposed listener. The server owns liveness, durable state, exact-once claim and logs. Same observer/launcher can be exercised against a branch without touching main. Disadvantages. Poll delay, explicit GitHub metadata handling for non-two-parent merges, and the filesystem runtime mounts need a real smoke test.

## Sketch B. GitHub merge event and server runner.

A workflow on closed pull_request with merged=true (or push plus merge metadata) submits a job to a server-installed self-hosted runner. The job claims the merge SHA in the same durable ledger, discovers verification skill folders, and launches the same isolated fresh Codex worker. A concurrency group alone is insufficient because a repeated delivery or workflow rerun would start duplicate maintenance after the first completion. This needs a self-hosted runner installation, signed-in credentials arrangement and a durable per-SHA claim. A throwaway-branch proof must permit the event's base branch to be overridden while retaining the exact same handler.

Advantages. Immediate event identity including squash/rebase and GitHub-visible job logs. Disadvantages. No such runner exists; it adds a long-lived service and management surface solely for this trigger. GitHub workflow trust and self-hosted runner eligibility add configuration unrelated to the existing signed-in server. Prefer A for this machine.

## Principles read and choices changed

Encode Lessons in Structure made the trigger a server service and product edit scope a read-only mount rather than prose. Make Operations Idempotent made merge SHA the durable run key and eliminated repeated session launches on repeated polls. Prove It Works requires an actual Codex session/thread event and the deployed trigger path in the throwaway-merge proof, not a stub process.
