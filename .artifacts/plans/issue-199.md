# Issue #199 — Web push device signup and reusable sender

## Goal

Todd signs in to the **Factory** HTTPS origin on Android and Windows, grants browser notification permission once on each, and registers two independent device subscriptions. An operator can submit a plain line, an exact Factory link, and a stable event key to one server-side sender; it attempts delivery to every current device, durably deduplicates confirmed push-service acceptances, retries only definitely unaccepted sends, marks ambiguous outcomes unresolved, and reports expired subscriptions. A test notice with its link must visibly arrive on both of Todd's devices before the UAT criterion is checked. A push-service acceptance is **not** proof of device display.

## Scope

In: Factory-origin authenticated signup UI/API, same-origin service worker, VAPID configuration, protected subscriptions, PostgreSQL send ledger, reusable local sender entry point, installation/migration instructions, integration coverage, exceptions-list row, operator-assisted UAT. Out: changing the existing Factory wait detector, watcher/Discord retirement (#200), Monday-note integration, root Julia Next.js site, claimed exactly-once delivery, guaranteed 24-hour display, infrastructure changes performed by the Factory sandbox, or claiming Todd-controlled device UAT from simulations. #181 is the parent; #199 is its first phase, not a duplicate of #200.

## Design decisions and rejected alternatives

- Attach signup routes and service-worker response to the **existing authenticated Factory server**, assembled through `factory.prepare()` in `ops/factory/app/src/mastra/index.ts`; do not add signup to `app/page.jsx` (a different app). Inspect the installed, pinned `@mastra/core`/`@mastra/factory` route API during build and use its supported server route/auth hooks. Explicitly require an authenticated user identity on signup and mutation routes; with auth disabled, fail closed. Serve only the service-worker script without credentials where the browser requires it; constrain its scope to the Factory push path. Mutations must reject cross-origin requests even when a WorkOS cookie is present. Avoid a second login scheme or client-provided user ID.
- Use a dedicated PostgreSQL migration for subscriptions and `(event_key, device_id)` send outcomes rather than the Discord watcher's SQLite database. Store encrypted subscription endpoint/keys at rest using a dedicated, operator-provided encryption key; index by keyed endpoint fingerprint (not endpoint text). VAPID signing keys and the encryption key remain in the host's protected configuration, never repository files, browser responses, URLs, log lines, or issue comments. Limit accepted push-service endpoint origins to an operator-managed allowlist, reject localhost/private/unexpected destinations and redirects, and require HTTPS; validate the browser's subscription shape and maximum lengths. Keep link validation confined to the configured Factory public origin and `/factories/` deep-link prefix. Render plain line as text, never HTML.
- Expose a reusable server-side `sendPushEvent({ line, link, eventKey })` and a non-HTTP local CLI consuming one JSON request on stdin, independent of the Factory application bootstrap. #200's Python watcher can invoke that CLI later without coupling to the current Discord sender. Use a maintained Web Push implementation for VAPID/TTL instead of hand-building encryption. Request TTL=86400 seconds; the push service may shorten it. Claim a per-device ledger row **before** sending so a crash or lost acknowledgment cannot trigger a duplicate: confirmed service acceptance is terminal; known rejection may be retried with bounded backoff; expired/invalid subscription is deactivated and reported; timeout/unknown network outcome is terminal `unresolved` pending diagnosis, not automatically replayed or labeled delivered. The operation reports per-device outcomes without exposing endpoint/key material. No service-side infinite retry worker is required for this card; later invocations with the same key can retry due, definite failures.
- Reject alternatives: a public sender endpoint (unneeded secret-bearing attack surface), push directly from the root Julia site (wrong authentication and origin), reuse of Discord-specific watcher ledger (wrong identity/storage), and assuming an HTTP success demonstrates a notification displayed on either device.

## Phases

### 1. Prove the authenticated signup boundary, then implement it

- In `ops/factory/app/`, first add a failing integration test exercising the real mounted Factory HTTP route with an authenticated fake/session and a denied/unauthenticated session: load signup page/config (public VAPID key only), register two distinct browser subscriptions, re-register one without duplicating it, reject cross-origin mutation, malformed/unapproved endpoint and an auth-disabled route. Include service-worker registration/scope and a simulated push event that shows a plain-text notice whose click opens only the validated Factory link. Confirm red before changing production code.
- Add small signup/worker route module(s) under `ops/factory/app/src/mastra/`, mount them in `index.ts` using the pinned route API; wire the browser `PushManager.subscribe` permission flow and minimal accessible device-state/error text. Use the server's authenticated principal rather than trusting signup payload ownership. Add the SQL migration under `ops/factory/` and subscription persistence under the same app source tree. Ensure no subscribed secrets/endpoint values reach route responses beyond what the browser needs; no caching of personalized signup responses. Prove green with the route integration test and a PostgreSQL-backed integration test against isolated tables, not only a mocked database. No production install in this phase.

### 2. Prove ledger semantics, then implement sender and deployable assets

- First add a failing sender integration test (`node:test`, same conventions as `ops/factory/app/*.test.mjs`) against isolated PostgreSQL tables and a local fake push transport: two devices get one accepted attempt each for the same event key; repeat sends do not repeat confirmed attempts; known rejection becomes due only after bounded delay; expired subscription is disabled and reported; timeout/ambiguous result stays `unresolved` after restart/new sender instance and is never described as delivered. Test encrypted subscription persistence, safe log output, valid link restrictions, TTL=86400, and concurrent same-key invocation claiming only one attempt per device. Do not put real VAPID keys or endpoint URLs in test output. Confirm red then make green in small increments.
- Add a separate `push-sender.ts` (transport injected at its public seam) and `push-send.mjs` stdin CLI in `ops/factory/app/`, required direct Web Push/PostgreSQL dependencies in `package.json`/lockfile, and SQL migration. Use transaction/unique constraints and durable statuses for restart/concurrency safety. Avoid importing `index.ts` in the CLI: it starts the Factory controller. Installer `ops/factory/install.sh` must include every new source/worker/CLI asset in its explicit file manifest; extend `ops/factory/install.test.mjs` to prove missing required assets fail without disturbing the old install and a successful staged install includes them. Add sender entry to `ops/factory/README.md` exceptions list, and document operator-only migration, protected env keys, VAPID public-key publication, endpoint-origin allowlist, manual test notice, log/status inspection, and rollback in the Factory README or a linked `ops/factory/` runbook. Do not log secret config during validation or rollback.
- Verify `npm ci && npm run check && npm run build` and focused `node --experimental-strip-types --import ./register-typescript-esm.mjs --test <new-tests>` in `ops/factory/app`; run the root CI checks (`.github/workflows/ci.yml`) and `node --test ops/factory/install.test.mjs`. If route tests reveal pinned Factory limitations, adapt to the supported server extension point **without** bypassing WorkOS/platform authentication, and record the change and new test.

If the install, privileges, real auth, or HTTPS service-worker scope fails, roll back the application and stop; a schema migration must be backward-safe and separately reversible.

Record which device displayed what and when; verify two distinct active subscriptions and per-device confirmed push-service outcomes, while distinguishing service acceptance from on-device receipt. Persist event/device outcome, attempt count and retry deadline so operators can inspect definite failures and unresolved attempts after restart. Log signup success/failure as safe counters/outcomes; log migration/version and deployed commit at install. Health/runtime proof counts active subscriptions and sends by state without exporting private subscription contents. Do not label push-service acceptance as displayed.

## Risks

- The live browser/auth route shape must be verified against the pinned Factory/Mastra APIs during build; a bypass of existing auth is unacceptable. Same-origin mutation and endpoint allowlisting protect against CSRF and server-side request forgery.
- Push acceptance and 24-hour TTL are best-effort service properties, not proof of receipt/retention. Ambiguous requests must not be replayed automatically; a known rejection must not be marked delivered.
- Current host PostgreSQL permissions, outbound push reachability and browser worker scope have not been proven in this sandbox. Runtime checks must be explicit before any completion claim.
- Todd's devices are outside machine/Factory operator control; this is a UAT handoff constraint, not a reason to invent evidence or modify Factory's wait watcher prematurely.
