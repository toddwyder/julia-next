# Issue #146 — Isolate Factory agent commands with Mastra bubblewrap

## Goal

Julia Factory's **local-provider** agent shell commands run under Mastra's native Linux bubblewrap isolation, not under the unrestricted Factory service account. Before merging, demonstrate on Julia's Factory server that absence or failure of bubblewrap is visible and never falls back to an unisolated command; that Factory keys/data are inaccessible; and that a disposable Git fetch/commit/push works with only intended credentials. Record that general internet access is enabled and accepted, along with limitations. After installation, take a real Factory card through planning and review. **Stop and report rather than merge** if the native backend cannot enforce the filesystem/credential boundary or maintain the Git workflow. Orca shutdown and reachability belong to #144, not this release gate.

## Verified baseline and framework map

- `ops/factory/app/src/mastra/index.ts:371-394` selects Platform, E2B, or local; the local branch constructs `LocalSandbox` with `workingDirectory` and `env`, but no `isolation`. Its allowlisted environment at lines 257-284 does **not** deny host file access. `ops/factory/install.sh` installs this repo-owned source; `ops/factory/install.test.mjs` checks staged copying, secrets retained and patch/build sequence, not isolated command behavior. The Factory app dependencies were installed in this checkout for the earlier tests; the available `bwrap 0.9.0` ran isolated commands here, **not evidence for a bound session in the installed Factory service**. Both touched Factory sources have only commit `1bcd527` (#145) in this checkout's history; the isolation implementation remains uncommitted.
- Need → built-in feature → official reference: Linux shell isolation → Mastra `LocalSandbox` native isolation → [Mastra LocalSandbox reference](https://mastra.ai/reference/workspace/local-sandbox); network and mounts → `nativeSandbox` on that same local sandbox → [Mastra sandbox overview](https://mastra.ai/docs/sandbox/overview); lifecycle visibility → Mastra sandbox command results and `getInfo().metadata.isolation` → [Mastra workspace sandbox reference](https://mastra.ai/reference/workspace/sandbox). The map is also posted on issue #146.
- The shipped `@mastra/core@1.71.0` declarations (`dist/workspace/sandbox/{local-sandbox,native-sandbox/types}.d.ts`) and implementation in the published package ([npm tarball](https://registry.npmjs.org/@mastra/core/-/core-1.71.0.tgz)) are the version-specific source of truth: `isolation: 'bwrap'` is supported; `nativeSandbox.allowNetwork` defaults to false and, when true, omits `--unshare-net` (general host networking, **not** Git-only egress); default bubblewrap command mounts system paths read-only, workspace read/write, and `/tmp` tmpfs. `bwrapArgs` **replaces** the default policy, not an additive Git allowlist. Constructor rejects a missing `bwrap` executable; runnable user namespaces still require an actual command proof. Never use `detectIsolation()` to select `'none'` on failure.
- Checked and rejected: Platform/E2B (paid or different provider), a Mastra patch, custom wrapper/proxy/network controller (no approved exception), custom `bwrapArgs` (replaces the safe defaults and still does not implement a Git egress allowlist), and fallback-to-none. Native support should be used unchanged; no new custom piece or exception is authorized.

## Scope

**In:** make the existing local `LocalSandbox` explicitly require `isolation: 'bwrap', nativeSandbox: { allowNetwork: true }`; add no extra host binds or custom args; test observable command failure/access via the public sandbox API; record installation, rollback and installed Factory proof in `ops/factory/README.md`, `docs/agents/factory-platform-auth-change-log.md` (or the current Factory operator change log), and the PR. Confirm a post-install real card's planning/review behavior and any valid #137 cross-evidence.

**Out:** shutting down Orca (#144), changing Platform/E2B selection, changing Mastra package code, provisioning a paid sandbox, silently loosening filesystem isolation, building a custom network filter/credential broker, claiming #137 done from this card alone, or putting secrets/canary values into committed records.

## Risks

- Pinned backend detects executable presence, **not** whether unprivileged user namespaces are permitted on the real server: run the actual Factory command path before merge.
- `allowNetwork: true` provides general internet access, explicitly approved by Todd on 2026-09-28. It does not enforce a network allowlist; do not present Git success as proof of restricted egress. Filesystem and credential denial remain mandatory.
- Default bwrap system read-only binds may expose surprising paths; explicit stat/read probes must cover the **real** key, DB, env, repo credential and service-home paths. Host/mount topology or Git helper configuration may make either side of the proof fail.
- Factory's other tools or background processes may bypass command isolation; validate through real Factory sessions, not just direct `LocalSandbox.executeCommand`.
- Deployment before merge changes a running service; stage under the operator's backup/rollback process and include evidence before merge. Never print secrets or push to a non-disposable branch.
