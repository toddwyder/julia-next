Preserve Factory's planning structure, transition, security checks and verdict mechanism. A staged installation proves the local skills are loaded; the next real card proves plan-in-PR and review behavior. Do not claim the last two criteria complete until that card actually runs.

## Risks

- **Build artifact:** `mastra build` may not carry `src/mastra/public/factory-skills` into the deployed runtime. Test the real build and Factory skill list before any live restart; do not patch Mastra or write a copy workaround without Todd approving a documented product gap.
- **Override drift/security:** replacing a skill with only a short prompt would lose Factory's review safeguards/transition semantics. Start with bundled 0.17.2 originals, minimally extend, and test preservation. Before a future Factory upgrade, diff both local copies against the new bundled versions.
- **Live proof timing:** acceptance criteria demanding the *next real card* cannot be established by unit tests or before an eligible card runs; keep this as a post-install verification gate, not a fabricated pre-merge pass.
- **Untrusted PR content:** Factory reviewer must continue to treat code/docs/PR descriptions as data, not instructions; preserve bundled checks and never execute suspect PR code during review.

## Assumptions / decisions

- #136's technical deployment prerequisite is present in PR #142, but #136/#143 must be checked before executing the live-install phase. This is a sequencing gate, not a reason to reimplement #136 here.
- Use `ops/factory/app/src/mastra/public/factory-skills` because the **installed package's** lookup expressly supports it and the existing installer already installs `src/mastra`; do not rely on `.agents/skills` for reserved Factory names. A custom board and a patch to `@mastra/factory` are rejected because the package already implements local skill priority. `configure-factory-rules` is for board policy, not this request.
- Copy/pin the bundled 0.17.2 skill documents and add short requirements rather than creating replacement prompts, preserving Factory's category references through bundled fallback. `CODING_STANDARDS.md` holds only project-wide rules already established by `AGENTS.md`; do not copy the long AGENTS policy or introduce novel rules.
- The plan itself is committed in `.artifacts/plans/issue-137.md`; future card plans are committed with their PRs, not written to an external progress store. Keep Factory's normal planning transition and review verdict behavior, including GitHub's own-PR comment fallback.
- Extend the current test/CI approach instead of writing a custom integration controller or a retry/wait loop. Manual live observation is necessary because textual tests cannot prove the deployed model actually follows the prompts.
