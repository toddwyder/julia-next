# Issue #154 — Recover Factory wait alerts rejected by ntfy HTTP 429

## Goal

A definitely rejected ntfy HTTP 429 must not permanently consume a Factory wait alert. Retry only that rejection after the documented rate-limit windows, at most twice per wait, without sending a second alert for an uncertain result or for a successful send. Leave #148 open until a naturally occurring new session question or plan review produces exactly one correct phone and Windows alert. Do not manufacture a wait for acceptance.

Preserve the existing SQLite ledger, stable per-wait notification identity, one-minute systemd timer, read-only Factory query, subscribed gate, and legacy ledger migration. No new service, loop, or hand-built progress file.
- Out: changing wait selection in `wait-alerts.sql`, notifications for automation suggestions/other decisions, automatically replaying old `attempted` rows (the old schema does not distinguish 429 from a timeout), changing Factory state, altering ntfy topics or subscriptions, and claiming a real device delivery from a mocked test.
- Existing tools checked: Factory 0.17.2 exposes waits but does not send both device alerts; its existing watcher is the approved exception recorded in `ops/factory/README.md`. Python `urllib.error.HTTPError` exposes a received 429, `sqlite3` persists retry state, and the existing systemd timer schedules runs. No Mastra/Factory modification or second scheduler is justified. Framework map posted on #154.
- History: PR #150 introduced the watcher (commit `f1e5562d25`); commit `90e2e379c2` narrowed alerts to direct Todd waits and added timeout/no-retry coverage. `deliver()` currently commits `attempted` before `publish()` (`ops/factory/wait-alerts.py:101-113`); on HTTP 429, `urlopen()` raises before status becomes `sent`, and the next timer run skips the key. ## Framework map

| Need | Built-in feature used | Official reference |
| --- | --- | --- |
| Know when to retry | ntfy's request bucket refills (default one request per 5 seconds); a configured daily message allowance resets at midnight UTC | [ntfy rate limiting](https://docs.ntfy.sh/config/#rate-limiting) |
| Identify a definite HTTP rejection | `urllib.error.HTTPError.code` vs a transport timeout/exception | [Python HTTPError](https://docs.python.org/3/library/urllib.error.html#urllib.error.HTTPError) |
| Preserve retry decisions across invocations | Existing Python `sqlite3` connection and committed transactions | [Python sqlite3](https://docs.python.org/3/library/sqlite3.html) |
| Run at the due time without a polling loop | Existing one-minute `julia-factory-wait-alerts.timer` | [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html) |

### 2. Handle a sustained 429 safely and make outcomes observable

- Tests first, one behavior at a time: (a) two consecutive 429s: after the first 60-second attempt, the second due time is the *next UTC midnight plus one minute* (at least 60 seconds after rejection); a timer call before then sends nothing; a success then sends exactly once; (b) a third 429 leaves a terminal `rate_limit_exhausted` state that does not retry on any later run; (c) after a due claim, a timeout or simulated process interruption remains `attempted`, never retryable; ordinary first-try timeouts likewise remain claimed; (d) seed the pre-fix ledger with `attempted` and old occurrence-suffixed entries and assert they are never resent; (e) verify service output and failure output contain no topic, wait key, link, credentials, or raw exception URL. Show each new behavior test red before its minimal production change. Use fixed UTC clock values crossing midnight instead of sleeping.
- Minimal change: count only definite received 429s; permit at most three HTTP publish attempts for a key (initial + two retries). First rejection waits at least 60 seconds (more than the documented default bucket refill); second rejection defers until after the documented daily reset at midnight UTC; third leaves a terminal status. On every due retry, claim `attempted` and commit before publishing so a crash/timeout can never become a resend. Do not retry other HTTP statuses or network errors. Treat an ordinary non-2xx response as non-retryable unless it is an actual received 429. A 429 can stop the current cycle without marking later waits attempted; they remain available at the next timer tick.
- Observability: replace the existing success journal line containing `wait_key` and `link` with a sanitized event including wait kind, outcome (`sent`, `rate_limited`, `rate_limit_exhausted`, or `uncertain_failure`), rejection count where relevant, and next due time for a scheduled retry. Never print the topic, key, link, request body, raw exception, or exception URL; sanitize the top-level error path too (including HTTPError and unexpected failures). Log one event per state transition, not once per skipped minute. Keep ledger status/rejections/retry_at as durable operator measurements; do not log per-wait IDs. Retain existing operator-only `--dry-run` functionality unchanged, and do not paste its output into public issues.

## Risks

- Received HTTP 429 is treated as rejection before publish; timeouts and crashes remain ambiguous. Never bulk-replay old `attempted` rows or retry after a success. A quota beyond ntfy's documented request/daily windows can outlast the bounded schedule; the exhausted state must be conspicuous in the sanitized journal for operator handling, not silently loop forever. A short burst of newly seen waits can itself hit a shared visitor limit; stopping the current run on 429 avoids repeated work within that cycle, but deferred waits are seen on later one-minute cycles. Sanitizing current success and top-level error output is required because the HTTP error URL contains the private topic.

## Assumptions

- Rejected alternatives: immediate retry or an in-process sleep loop can hammer a depleted quota and conflicts with the existing timer; retrying every `attempted` row duplicates ambiguous sends; a new queue/table or Factory-side controller expands the approved exception; relying only on an unverified `Retry-After` header can leave a wait stranded. Extend the existing ledger and reuse the timer instead.
- The documented ntfy request bucket and UTC-midnight daily reset apply to the current `ntfy.sh` topic; no documented `Retry-After` contract was found, so do not depend on an unverified response header. The 60-second first delay and next-UTC-midnight second delay are conservative windows, not a promise of five-minute delivery under a full daily quota. At most three HTTP attempts per wait is the bounded policy; further 429s need operator investigation.
- The existing ledger can be extended in place without migrating ambiguous historical outcomes; the existing `attempted` rows stay suppressed. Stable per-wait ntfy identity and SQL selection are unchanged. Todd's already-stated no-staged-proof decision and the #148 real-world check remain in force.
